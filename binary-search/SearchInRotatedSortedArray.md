# 33. Search in Rotated Sorted Array

- 링크: https://leetcode.com/problems/search-in-rotated-sorted-array/
- 유형: 이분 탐색 (값 찾기, [노트](https://github.com/DaeunSon/algorithm-notes/tree/main/04-binary-search)의 틀 1) + 어느 절반이 정렬됐는지 먼저 판단
- 날짜: 2026-10-29
- 상태: 정답을 보고 작성, 통과. **꼭 재풀이** (안 보고 다시 짜기)

## 접근

회전된 배열에는 값이 뚝 떨어지는 지점(`7 → 0`)이 딱 한 군데 있다. `mid`로 반을 자르면 그 지점은 한쪽에만 들어가므로, **나머지 한쪽은 반드시 정렬돼 있다.**

1. `nums[left] <= nums[mid]`면 왼쪽 `[left..mid]`가 정렬, 아니면 오른쪽 `[mid..right]`가 정렬
2. **정렬된 쪽**은 양 끝 값만 보면 target이 그 안에 있는지 알 수 있다
   - 왼쪽 정렬: `nums[left] <= target < nums[mid]`이면 `right = mid - 1`
   - 오른쪽 정렬: `nums[mid] < target <= nums[right]`이면 `left = mid + 1`
3. 정렬된 쪽에 없으면 **반대쪽**으로 간다 (반대쪽이 정렬됐는지는 상관없음)

`[4,5,6,7,0,1,2]`, target 0

| left | right | mid | nums[mid] | 정렬된 쪽 | target이 그 안에? | 이동 |
|---|---|---|---|---|---|---|
| 0 | 6 | 3 | 7 | 왼쪽 `[4..7]` | 없음 | `left = 4` |
| 4 | 6 | 5 | 1 | 왼쪽 `[0..1]` | 있음 | `right = 4` |
| 4 | 4 | 4 | 0 | | 찾음 | 4 반환 |

## 시간복잡도 / 공간복잡도

- 시간: O(log n)
- 공간: O(1)

## 막혔던 점

- 정렬이 깨져 있어서 `nums[mid]`와 target만 비교해서는 어느 쪽으로 갈지 정할 수 없었다. **정렬된 절반을 먼저 찾고, 범위 비교는 그쪽에서만** 한다는 생각을 떠올리지 못했다.
- `nums[left] <= nums[mid]`의 `=`가 필요하다. 원소가 2개면 `left == mid`라 왼쪽 절반은 원소 1개이고, 원소 1개는 정렬된 것으로 봐야 한다.
  - `<`로 쓰면 `[3,1]`, target 1에서: `mid = 0`, `3 < 3` 거짓 → 오른쪽이 정렬이라고 판단 → `1 >= 3` 거짓 → `right = -1` → -1 반환 (틀림).
- `nums[mid] == target`은 먼저 확인하므로 범위 비교에서 `mid` 쪽 끝은 `<`, `>`로 빼도 된다.

## 재풀이할 때 확인

- [ ] 반으로 자르면 왜 한쪽이 정렬돼 있는지 말로 설명할 수 있다
- [ ] 안 보고 "정렬된 쪽 판단 → 그쪽 범위에 있나 → 아니면 반대쪽"을 다시 짜기
- [ ] `[4,5,6,7,0,1,2]`에서 target 0 → 4, target 3 → -1
- [ ] `[1]`에서 target 0 → -1, `[3,1]`에서 target 1 → 1 (`<=`의 `=`가 필요한 경우)

## 재풀이 기록 (2026-11-06)

- 결과: 24분, 힌트 없이 통과. 다만 **O(n) 풀이**라서 문제가 요구한 O(log n)은 아님 → 재풀이 필요
- 한 것: 꺾이는 지점(branch)을 `for`문으로 찾고, 두 구간에서 각각 찾기
- 처음엔 `mid ± 1`로 이분 탐색을 했는데 값을 건너뜀 → 원인은 **방향이 반대**였던 것(`nums[mid] > target`인데 `left`를 옮김). 이걸 `left++` / `right--`로 바꿔서 통과했지만, 그건 이분 탐색도 투 포인터도 아닌 한 칸씩 훑기
- 다음에 쓸 규칙
  - 이분 탐색: `nums[mid] > target`이면 답은 **왼쪽** → `right = mid - 1`
  - branch도 이분 탐색(틀 1, "처음으로 `nums[mid] < nums[0]`이 되는 곳")으로 찾아야 전체가 O(log n)

## 재풀이 기록 (2026-11-08)

- 결과: △ (혼자 통과, 하지만 아직 O(n))
- 좋아진 점: 지난번에 반대로 썼던 이분 탐색 방향을 이번엔 맞게 씀(`nums[mid] > target`이면 `right = mid - 1`). 두 구간 모두 진짜 이분 탐색.
- 남은 점: 회전 지점(`index`)을 여전히 `for`로 찾아서 전체가 O(n).
  - 회전 지점 찾기는 First Bad Version과 같은 모양: `nums[mid] < nums[0]`이 false…false, true…true로 나뉘므로 틀 1 + answer로 "처음 true"를 찾으면 된다.
- 헷갈린 점과 정리
  - 투 포인터인지 헷갈림 → 문제에 **O(log n)**이 적혀 있고 **값 하나**를 찾으면 이분 탐색. 투 포인터는 짝/합.
  - `left <= right`의 `=` → 틀 1은 `mid - 1` / `mid + 1`로 `mid`를 버리므로 `left == right`일 때 남은 한 칸도 확인해야 한다. `=`가 없으면 `[5]`, target 5에서 반복문이 안 돌아 -1.
